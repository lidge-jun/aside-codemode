## 측정

질문은 몇 배 빨라졌느냐가 아니라 어떤 구간을 묶어야 완료 시간이 줄어드느냐다. 그래서 비교 대상은 전부 "잘 쓴 네이티브 경로"이고, 배치가 지거나 비기는 워크로드도 그대로 싣는다.

네 워크로드 x cold/warm x 30쌍 = 480 실행, mac 1대. 여덟 버킷 전부 오류율 0.0%, 선두 15/15, p95 산출(n=30). 워크로드 안에서는 30회 전부 같은 답이 나왔으므로 시간 차이는 실패를 잰 결과가 아니다.

| 워크로드 | 묶는 단위 | warm native | warm 배치 | cold native | cold 배치 |
|---|---|---|---|---|---|
| 알려진 버튼 1회 클릭 | (없음) | 1249 ms, 1콜 | 1244 ms, 1콜 | 1266.5 ms | 1263.5 ms |
| 처음 보는 페이지 탐색 | 세션 | 3257 ms, 3콜 | 1249 ms, 1콜 | 3275.5 ms | 1266 ms |
| 독립 6쪽 읽기 | 탭 동시성 | 8413 ms, 1콜 | 4429.5 ms, 1콜 | 8441 ms | 4414 ms |
| 파일 6개 집계 | 프로세스 | 399.5 ms, 6콜 | 82 ms, 1콜 | 433 ms | 115 ms |

원자료는 `eval/out/<워크로드>-<모드>.jsonl`, 표는 같은 이름의 `.md`다. 유휴 대기는 시계 밖이고 행마다 `mode`와 `idleMs`가 붙는다.

**네 결과를 하나의 배수로 합치면 안 된다.** 묶는 단위가 서로 다르다.

*알려진 버튼 1회 클릭은 무승부다.* 1244 대 1249는 0.4%이고 표준편차 26ms 앞에서는 잡음이다. 쌍별로 보면 배치가 빠른 쌍 17, 느린 쌍 11, 동률 2로 승패가 갈린다. 헬퍼를 디스크에서 읽어 eval하는 비용은 repl 기동과 페이지 로드가 지배하는 1250ms에 묻혀 이 해상도에서는 보이지 않는다. 한 번의 클릭을 배치로 바꿀 이유는 속도에 없다.

*처음 보는 페이지 탐색의 62%는 세션을 두 번 덜 여는 값이다.* 배치가 탐색을 빠르게 하는 것이 아니다. native 3콜의 콜별 중앙값은 768.5 + 1242 + 1239인데, 2·3번째 콜은 단일 클릭 한 번(1249)과 같은 값이다. 아낀 2000ms는 정확히 그 두 번의 페이지 로드다. 잘못된 셀렉터에서 재관찰까지 걸린 시간은 중앙값 6~7ms로 복구 자체는 싸다. 3콜이 된 이유는 `aside repl`이 호출마다 세션을 새로 만들어 탭을 넘기지 못하기 때문이고, read 호출이 "이전 클릭이 남아 있지 않다"를 단언해 그 제약을 매 실행 확인한다. 한 native 프로그램 안에서 observe-act-read를 하면 이 차이는 대체로 사라질 것이고, 그 비교는 이 자료에 없다.

*독립 6쪽 읽기의 47%는 탭 두 개가 겹친 값이다.* 8413/6 = 쪽당 1402ms, 배치를 2탭 3파도로 보면 파도당 1476ms, 비 1.90으로 2병렬 이론값 2.0에 가깝다. 쪽 하나가 빨라진 것이 아니라 겹친 것이고, native도 탭 두 개를 직접 열 수는 있다. 여기서 측정한 것은 "한 장씩 도는 손 루프 대 limit 2 헬퍼"다.

*파일 집계의 79%는 warm에만 해당한다.* cold는 73.4%다. warm에서 per-file 6콜은 각 66ms로 균일하고 합 396ms가 전체 399.5ms와 같다 — 검색 자체는 한 프로세스 안에서도 82ms에 끝나므로 차이 317ms는 프로세스를 다섯 번 더 띄운 값이다. 콜드 가산은 두 경로 모두 약 +33ms로 같고, 40%로 보이는 것은 분모가 82ms이기 때문이다. 콜드 6콜에서도 첫 호출만 100ms이고 나머지 다섯은 66ms다.

*cold와 warm의 차이는 브라우저에서 작다.* 여섯 브라우저 버킷의 cold−warm은 −0.35%에서 +1.57% 사이이고, independent-reads 배치는 오히려 cold가 15.5ms 빠르다. CLI만 유휴 다음 첫 프로세스 기동이 세금으로 붙는다.

**말할 수 없는 것 하나를 명시한다.** 090은 "단일 native 경로의 중앙값 회귀 10% 이내"를 목표안에 두었다. 이 캠페인은 그것을 판정하지 못한다. 회귀는 같은 경로를 도입 전후로 비교하는 말인데 이 자료에는 native 클릭의 도입 전 값이 없다. 1249는 같은 캠페인의 대조군이지 기준선이 아니다. 감사자 두 명이 각각 같은 이유로 이 문장을 기각했다. 말할 수 있는 것은 "1클릭을 배치로 바꿔도 native보다 느려지지 않았다"(0.4%, 승패가 갈림)까지이고, 10%라는 여유는 변동계수 2%인 자료에 비해 면죄부에 가깝다. 이 항목은 충족하지 않은 채로 둔다.

**아직 세지 않은 것.** 090의 G5 사용성 게이트는 수동 세션 설계다. 자동 대리 지표(정답, 왕복 수, 복구 시간)는 처음 보는 페이지 탐색 워크로드가 기록하지만 그것이 사용성 세션을 대신하지 않는다. 돌리지 않았고 통과로 세지 않는다.

## 계획과 달라진 것

090 표의 fixture 중 `test/fixtures/batch/`, `test/fixtures/serve.mjs`, `test/fixtures/discovery/keys.json`, `test/fixtures/slow-click/`는 저장소에 없다. 앞의 둘은 wp8에서 만들었다가 지웠다 — Aside 브라우저가 이 기기의 loopback에 닿지 못해 로컬 http가 프로브 전송이 될 수 없었고(`data:` URL로 대체), 쓰지 않는 파일을 남기면 다음 사람이 그걸 경로라고 믿는다. 뒤의 둘은 해당 phase가 픽스처 파일 대신 테스트 안에서 데이터를 만드는 쪽을 택했다. 게이트 명령은 그에 맞춰 실제로 존재하는 테스트 파일을 가리킨다.

## 여기서 멈춘다

`main` 병합, 태그, release, npm publish, macmini 배포는 이 계획의 산출물이 아니다. 금고 자동입력, 캡차 실해결, 실제 계정 로그인 성공도 마찬가지다. 실계정 루트에는 읽기 전용 `doctor`만 돌렸고 설치는 하지 않았다 — 사용자 환경을 바꾸는 일이라 별도 결정이다.

**NEEDS_HUMAN.** RC 후보와 게이트 증거는 위에 있다. G5와 나머지 세 워크로드를 채울지, 이대로 승인할지는 사용자 판단이다.
