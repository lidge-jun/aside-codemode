# 090 — wp10: 통합·성능 평가와 RC 고정

## 측정 설계

질문은 「모든 작업이 몇 배 빨라졌나」가 아니라 **어떤 구간을 묶어야 전체 완료 시간이 줄어드는가**다.
비교 대상에는 잘 작성된 네이티브 REPL 배치도 포함한다. 코드모드가 그보다 느리면 그 사실을 그대로 적는다.

| 워크로드 | 비교 경로 | 기록할 지표 |
|---|---|---|
| 알려진 버튼 1회 클릭 | native ref / native CUA / helper / CLI | 준비 포함 지연, 결과 확인, wrong-target 수 |
| 처음 보는 페이지 탐색 | native 자유 선택 / 강제 code mode | 정답, 불필요한 왕복, 복구 시간 |
| 독립 9개 페이지 읽기 | native 순차 / REPL 배치 / helper / CLI | 전체 완료시간, 회수율, peak tabs, 실패 격리 |
| API·파일 대량 집계 | 기존 native / batch | 토큰, bytes, 호출 수, 동등 정답 |

- 범주당 최소 30쌍의 순서 교차 비교. cold와 warm을 분리한다.
- 중앙값과 **각 실행값**과 오류율을 함께 공개한다. 적은 표본의 p95를 운영 지표처럼 쓰지 않는다.
- 목표안(합의 대상이지 실측이 아니다): 대표 batch 중앙값 20% 이상 단축, 단일 native 경로 중앙값 회귀 10% 이내.
  정답률을 낮춰 통과시키지 않는다. 네이티브를 선택해 불필요한 배치를 하지 않은 것도 성공으로 센다.
- 시각·인증이 섞인 흐름은 자동 측정에서 제외한다. 사용자 개입이 필요한 구간이라 별도로 기록한다.

## 게이트

| 게이트 | 시험 집합 | 합격 기준 |
|---|---|---|
| G0 계약 | runtime validator와 discovery의 같은 fixture | 허용/거절 일치 (wp7 F12) |
| G1 정답 | 역순 완료, 중복 URL, 누락, ref 변경, 최종 관찰, cache 옵션 | 틀린 대상·출처·정답 은폐 0건 |
| G2 실행 수명 | 느린 open/close/action, abort, 프로세스 종료, 재개 | 누락된 부작용 상태 0건, unsafe 자동 retry 0건 |
| G3 native 통합 | 혼합 native+batch, 이미지 입력, CUA 대상 격리 | 선택한 fixture의 실제 결과와 일치 |
| G4 배포 | clean install, upgrade, repair, uninstall, rollback | 사용자 수리 없이 성공 (wp9) |
| G5 사용성 | 새 에이전트 세션, 경로 선택 평가, cold/warm | 정답 유지, 단일 작업에 불필요한 우회 없음 |

## RC 고정

- G0–G5를 통과한 커밋을 RC로 **고정**하고, 검증 중 `dev`의 최신 HEAD를 따라가지 않는다.
- 한 번 만든 묶음을 mac과 Windows MINI에 설치한다. 같은 digest를 확인한다.
- macmini는 이번 범위 밖이다(사용자가 프로브 대상을 두 기기로 한정했다).

## 여기서 멈추는 것

`main` 병합, 태그, release, 세 기기 정식 배포는 이 계획의 산출물이 아니다.
RC 후보와 증거를 갖춘 상태에서 **NEEDS_HUMAN**으로 보고하고 사용자 승인을 기다린다.
금고 자동입력, 캡차 실해결, 실제 계정 로그인 성공도 같은 이유로 사용자 확인 항목이다.
